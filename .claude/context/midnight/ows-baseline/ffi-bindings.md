# FFI bindings — Node + Python

## Architecture (per CLAUDE.md and `bindings/`)

- **Node:** `bindings/node/` (NAPI-RS) → `@open-wallet-standard/core` npm package.
- **Python:** `bindings/python/` (PyO3 + Maturin) → `open-wallet-standard` PyPI package, module `ows._native`.
- **TS framework adapters:** `bindings/node-adapters/` — pure-TS, no Rust (viem, Solana, WDK).

Both bindings link `ows-lib` (the high-level FFI-facing crate per CLAUDE.md "Workspace layout"); they do not directly link `ows-signer` or `ows-core`.

## Chain-handling shape

CLAUDE.md "Chain extension points" claims:

> Once a `ChainType` variant is registered, FFI flows through automatically; verify TS/Python type hints if added.

In practice (from `bindings/node/src/lib.rs` head): chain identifiers cross the FFI boundary as **strings** — typically `chain_id: String`. The Rust side calls `ows_core::parse_chain(&chain_id)` to resolve to a `Chain`. Neither binding enumerates `ChainType` variants explicitly in its public API.

This means a new `ChainType::Midnight` variant + `KNOWN_CHAINS` entry would flow through automatically *for chain identifier handling*, but **does not** automatically expose any new operations (e.g., multi-key derivation, sync-state shapes, prover invocations) — those need new public functions in `ows-lib` and corresponding NAPI/PyO3 export decorators.

## Salient facts for delta vs. Midnight

- **String pass-through is robust to new chain identifiers.** Midnight's `midnight:mainnet` flows through automatically once `parse_chain` knows it, with no FFI changes needed for **chain-id handling**.
- **Multi-key derivation does not flow through.** OWS today exposes `derive_address(chain, ...)` returning a single string; Midnight's three-key-per-account model needs either (a) `derive_addresses(chain, ...)` returning a structured object, or (b) per-domain functions (`derive_shielded_address`, `derive_unshielded_address`, `derive_dust_address`). Each requires explicit FFI surface.
- **Type-hint files (`.d.ts`, Python stubs) need updates** to expose new structures (e.g., `MidnightAccount = { shielded: string, unshielded: string, dust: string }`).
- **No async/streaming surface for sync state** — the Midnight wallet's stream-based sync model (per `midnight-wallet/packages/runtime` per the raw-context index) doesn't have an obvious analogue in OWS's current FFI shape, which is request/response.
- **Wallet-vault file format is shared across bindings** (lives in `ows-lib/src/vault.rs` per workspace layout). New encrypted-key fields for Midnight (three keys per account) need to be backwards-compatible with the existing format or gated by version.
