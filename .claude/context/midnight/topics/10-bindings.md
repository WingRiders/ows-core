## Midnight surface that needs binding

Per 2c §B + §G:

### Per-account, multi-address derivation

Existing OWS:
```typescript
derive_address(chain: string, mnemonic: string, index?: number): string
```

Midnight extension. Two shapes:

**Shape A (per-domain):**
```typescript
derive_shielded_address(mnemonic: string, account: number, index: number): string
derive_unshielded_address(mnemonic: string, account: number, index: number): string
derive_dust_address(mnemonic: string, account: number, index: number): string
```

**Shape B (account-bundled):**
```typescript
derive_midnight_account(mnemonic: string, account: number): {
    shielded: string,
    unshielded: string,
    dust: string,
}
```

Shape B matches the wallet's mental model (one account, three addresses). Shape A composes with the existing `derive_address` shape.

### Recipe-based transaction lifecycle

Per 2c §B-03 / §B-06, the wallet's tx flow has 5 steps:
1. `transferTransaction(outputs, secrets, options) -> UnprovenTransactionRecipe`
2. `balanceUnprovenTransaction(...)` (or `balanceFinalizedTransaction`, etc.)
3. `signRecipe(recipe, signSegment) -> BalancingRecipe`
4. `finalizeRecipe(recipe) -> FinalizedTransaction` (calls prover-client internally)
5. `submitTransaction(tx) -> TransactionIdentifier`

Each step is a Promise. OWS bindings could:
- **Expose all five** (caller orchestrates, like the wallet's facade does). Maximum flexibility; matches wallet's API.
- **Bundle into one signing call** (`sign_midnight_transaction(...)`) that does all five internally. Simpler; closer to existing OWS `sign_transaction`. But hides the proving step's latency / failure modes.
- **Two-step (build + finalize)** — caller builds the recipe, OWS finalizes. Compromise.

### Sync state plumbing

Per `09-state-persistence.md`. Shapes:
- **Implicit:** binding methods read/write state from `~/.ows/midnight/...` automatically. Caller passes only `wallet_id`.
- **Explicit:** binding accepts `state: bytes` and returns `state: bytes` after each operation. Caller persists.

Implicit is closer to existing OWS pattern (vault is auto-managed). Explicit is closer to the scope's "state needs to be persisted between calls" language.

### Indexer URL config

OWS needs a way for the caller to set the indexer URL. Plausible: per-call argument, environment variable (`OWS_MIDNIGHT_INDEXER_URL`), or config file `~/.ows/config.json`. CLAUDE.md mentions `ows config` CLI commands; a `config set midnight.indexer_url <url>` flow fits.

### Prover URL / route config

Same pattern as indexer:
- If route C (hosted prover): `OWS_MIDNIGHT_PROVER_URL` or config.
- If route A (in-process Rust): no URL; CRS path / cache dir instead.
- If route B (WASM): the WASM blob shipped with the binding; no caller config.

Per [04-proving](04-proving.md), this is a phase-3 decision.

## TypeScript types (per 2c §J binding strategy)

Wallet uses `Effect + RxJS` internally. Public API uses `Promise + Observable`. OWS's existing FFI is Promise-based; Observables don't translate cleanly to NAPI.

For state subscriptions, two shapes:
- **One-shot poll:** `get_sync_state(wallet_id) -> SyncStateSnapshot`. Caller polls.
- **Callback channel:** OWS exposes a callback registration. NAPI supports threadsafe functions; PyO3 less idiomatic.

One-shot poll is simpler and matches the AI-agent use case better (agents don't need real-time pushes).

## Type-hint files

Per CLAUDE.md "Generated files," `index.d.ts` is regenerated by NAPI build. Adding a `MidnightAccount` type:

```typescript
export interface MidnightAccount {
    shielded: string;
    unshielded: string;
    dust: string;
}
export function deriveMidnightAccount(mnemonic: string, account: number): Promise<MidnightAccount>;
```

Python stubs (`bindings/python/.../*.pyi`) need analogous additions.

## CLI implications

`ows/crates/ows-cli/src/main.rs` exposes wallet/sign/policy/key commands per `../ows-baseline/`. Midnight extensions:

- `ows wallet create --chain midnight ...` — should derive all three Midnight addresses and print them.
- `ows wallet get <wallet_id> --chain midnight` — show three addresses + sync status.
- `ows sign transaction --chain midnight <tx-hex>` — must trigger the recipe lifecycle internally (or expose explicit subcommands).
- New: `ows midnight sync <wallet_id>` — explicit sync command (in case `sign` is too coarse).
- New: `ows midnight balance <wallet_id>` — show shielded/unshielded/dust balances.

Match scope-level commands to the connector API surface where possible.

## Vault file format

`~/.ows/wallets/<wallet_id>.json` carries encrypted mnemonic. For Midnight wallets imported from raw private keys (not mnemonic), the vault must store **three encrypted keys** (shielded sk, unshielded sk, dust sk) instead of one. Backward-compatibility: tag the vault entry with a `keys_per_chain: 3` flag, or version-bump the vault format.

## What this means for OWS

- **Three new public APIs (minimum):** multi-address derivation, recipe lifecycle bundling, sync-state access.
- **Type-hint files** must be updated; users will rely on them for IDE intellisense.
- **CLI extensions** for sync + balance + recipe steps.
- **Vault format** might version-bump for multi-key entries.
- **No async/streaming surface** for sync state today; we keep it that way (one-shot poll) unless agents need real-time.

## Second-pass refinements (2d / 2e / 2f)

**2e (connector v4.0.0) constrains the OWS↔AI-agent surface.** Per scope §8.4.2026, the OWS↔agent boundary is structurally analogous to the wallet↔dapp boundary; the connector is the closest reference. Implications:

- **Hex-string tx contract.** Connector returns and accepts hex-encoded tx strings only; recipe lifecycle hidden. OWS FFI can adopt the same opacity (small surface area, less version skew between OWS and agent), or expose recipe steps explicitly (more powerful, more API surface). The connector pattern is simpler.
- **Three-method address surface.** OWS FFI should expose `derive_shielded_address`, `derive_unshielded_address`, `derive_dust_address` (or one returning all three) — not unify into a single `derive_address` until the single-address proposal lands. Q-bindings-1.
- **Granular permission codes.** OWS FFI errors should include `PermissionRejected`-style structured error codes per method, not just generic `SignerError`. Phase 3 decides if OWS error catalog matches the connector's (`InternalError`, `Rejected`, `InvalidRequest`, `PermissionRejected`, `Disconnected`).
- **Proving delegation seam.** `getProvingProvider(keyMaterialProvider)` is a clean pluggability seam: dapp passes a `KeyMaterialProvider` (ZKIR + prover key + verifier key), wallet returns a `ProvingProvider` (`check`, `prove`). OWS can offer the same: an `OwsProvingProvider` Rust trait at the Rust core, exposed through FFI. Lets OWS support routes A/B/C without API breakage. Strong fit.

**2d (WalletEngine):** confirms multi-key surface (3 addresses per logical account, shared mnemonic, 5 hardcoded HD roles). FFI should:

- Expose `derive_midnight_account(mnemonic, account_index) -> { unshielded_external, unshielded_internal, dust, shielded, metadata }` — returning all five role-derived keys at one index. Mirrors `midnight-wallet/packages/hd`'s `RoleKey.deriveAllKeysAt(i)`.
- Expose **state operations** (apply_transaction, finalize_transaction, rollback_last_transaction, discard_transaction, spend, watch_for) at the FFI surface — these are the wallet's atomic operations per `Specification.md:456-465`. Without them, OWS bindings cannot host the wallet state machine.
- **Test vectors directly portable** for Rust unit tests: `WalletEngine/test-vectors/{addresses.json, keyDerivation.json}`. Add to CI under `bindings/{node,python}/test/midnight/`.

**2f (Lace) — production binding patterns:**

- **Branded value objects** (TypeScript `Brand.Branded<T, 'Name'>`) wrap raw addresses/network-IDs. OWS Rust port can use newtypes (`pub struct ShieldedAddress(pub [u8; 64])`) for the same compile-time safety.
- **Module map split** between `lace-extension` (browser) and `lace-mobile` (native) — `dapp-connector-midnight` is extension-only; `blockchain-midnight` is shared. OWS FFI is shared by Node and Python; no equivalent split needed, but worth noting for any future browser-extension binding.
- **Feature-flag gating without fallback** (`FEATURE_FLAG_MIDNIGHT_DAPP_CONNECTOR`) — Lace simply unloads the module when disabled. OWS should gate Midnight under a Cargo feature flag (`midnight`) that defaults off until v1, gated on by build flag.

## True 2g — wallet vs dapp SDK boundary (informs FFI layering, closes H-6 for FFI)

> Source: deep read of `raw-context/midnight-js/{AGENTS.md, CLAUDE.md, packages/}` and cross-reference with `raw-context/midnight-wallet/{AGENTS.md, CLAUDE.md}`. See [topic 06](06-connector.md) §"midnight-js vs midnight-wallet boundary" for the full boundary table.

| Package | One-line purpose | Dapp-relevant? |
|---|---|---|

| `types` | Shared interfaces for all midnight-js modules | fundamental |
| `network-id` | Network ID initialization for ledger WASM API | required for setup |

### Implication for OWS FFI layering

If OWS-core (Rust) is the wallet runtime, the boundary suggests:

- **`bindings/node/` and `bindings/python/`** expose the **wallet-side** API: signing (analogue of `WalletProvider.balanceTx`), key custody, state sync, vault. Mirror `midnight-wallet`'s package map.
- **`bindings/node-adapters/`** could host **dapp-side** SDK pieces — pure-TS, no Rust. Out of scope for v1; OWS targets the wallet runtime, not the dapp SDK.
- **In-process proving (route A)** lives inside OWS Rust core; invoked via the wallet-side FFI. midnight-js's `dapp-connector-proof-provider` proves via the wallet's `getProvingProvider()` — OWS implements that provider.
- **ZK config providers** (analogues of `fetch-zk-config-provider`, `node-zk-config-provider`) sit in the wallet runtime; OWS Rust can vendor `midnight-circuits` / `midnight-proofs` for the circuit-key store and expose load-from-disk / fetch-over-HTTPS variants behind a single trait at the FFI.

### What midnight-js does NOT include (verified for OWS scope)

- **No signing.** No key custody. No state machine. midnight-js never sees signing-key material — only public keys (`wallet-provider.ts:37-39`).
- **Tx flow stops at `UnboundTransaction`.** `WalletProvider.balanceTx()` produces `FinalizedTransaction` — that's where signing happens.
- **Boundary point** is the `WalletProvider` interface — midnight-js calls it, wallet implements it.

### Closes H-6 verdict (FFI-relevant slice)

**CLOSED.** Boundary is clean and zero-overlap. See [topic 06](06-connector.md) for the full responsibility table. **OWS-side action:** if v1 ships a Node SDK for *dapps* on top of OWS, mirror midnight-js's module split (`@ows-ntwrk/contracts`, `@ows-ntwrk/proof-provider`, `@ows-ntwrk/zk-config-provider`, etc.) — phase-5+ deliverable. Core OWS is the wallet runtime.

## Second-pass open questions

- **Q-bindings-1 (NEW from 2e):** OWS multi-address derivation API — three separate FFI functions (mirrors connector's three methods), or one returning all three (mirrors `midnight-wallet/packages/hd`'s `deriveAllKeysAt`)? Phase 3 picks; favor one returning all three for atomicity (caller can't forget one).
- **Q-bindings-2 (NEW from 2d):** State operation surface — does OWS expose all six WalletEngine state ops (apply/finalize/rollback/discard/spend/watch_for) at the FFI, or wrap them in a higher-level `Wallet` object? Tradeoff: granular = composable, wrapped = simpler API.
- **Q-bindings-3 (NEW from 2e):** OWS error codes — match connector's 5 codes exactly (`InternalError`, `Rejected`, `InvalidRequest`, `PermissionRejected`, `Disconnected`), extend with OWS-specific ones, or use OWS's existing `SignerError` shape?
- **Q-bindings-4 (NEW from 2e/2f):** Proving provider pluggability — expose `OwsProvingProvider` trait in Rust core; bindings forward to it. This is the cleanest seam for routes A/B/C. Phase 3 confirms.
